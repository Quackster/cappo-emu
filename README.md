### Starting the RMI registry

The server binds its remote objects (RMI stubs) into an RMI registry, so the registry must be running on port 1099 before the emulator starts. The registry also needs the full classpath on its JVM, otherwise it can't resolve the stub classes when a client/server looks them up. The command below runs the registry with that classpath already set:

```bash
CLASSPATH="target/classes:$(mvn -q dependency:build-classpath -Dmdep.outputFile=/dev/stdout)" rmiregistry 1099
```

- `target/classes` — the project's freshly compiled classes.
- `$(mvn -q dependency:build-classpath -Dmdep.outputFile=/dev/stdout)` — builds the full list of Maven dependency JARs and prints it to stdout, which is inlined into `CLASSPATH` in one pass.
- `rmiregistry 1099` — starts the RMI registry listening on port 1099.

### SSO ticket tokenizer

The client logs in by sending an SSO ticket; `SSOTicketParser` decodes it to recover the user id and authenticate. `SSOTokenizer` is the matching issuer — it mints a ticket that the parser will accept. The two are exact inverses, so a ticket generated by `SSOTokenizer.generate(userId)` round-trips through `SSOTicketParser` cleanly. The server prints a sample token at boot (`Server.java:141`).

A ticket is the **base64** of the plaintext `"<timeout>-<x>-<chunk>"`, where:

- `timeout` — unix seconds after which the ticket expires. The parser rejects any ticket whose `timeout` is already in the past, so it must be in the future when the client connects.
- `x` — an opaque integer. The parser ignores its value; it only uses it to rebuild the "public key" as `timeout + x`. Any value round-trips; `0` is fine.
- `chunk` — the user id, encrypted with a two-stage XOR.

The two-stage XOR (both stages repeat the shorter operand to match the length of the longer):

1. **tokenizer** = `ssoSecretKey` XOR `pubKey` (length = `ssoSecretKey.length()`, `pubKey` repeating), where `pubKey = (timeout + x)` as a string.
2. **chunk** = `"<userId>"` XOR `tokenizer` (length = `userId` string length, `tokenizer` repeating), one byte per character.

To decode, the parser rebuilds `pubKey` from `timeout` and `x`, re-derives the `tokenizer`, XORs `chunk` against it, and parses the result back into the integer `userId`. The two XOR passes are symmetric so encode and decode are the same operation.

Configuration:

- `sso.secretkey` in `Cappo.properties` (default `log#in#key`) — loaded into `Server.ssoSecretKey`. `SSOTokenizer` throws if this is unset. The secret **must match between issuer and server**, and since the client never sees it, you can change it to anything as long as both sides agree.
- **Charset** — cappo's wire layer treats strings as single bytes (`& 0xFF`, `new String(bytes)`), i.e. ISO-8859-1 semantics. `SSOTokenizer` therefore encodes/decodes the chunk with ISO-8859-1 explicitly so it is lossless and deterministic regardless of the JVM default charset. The parser, however, decodes the chunk with `new String(decodedBytes)` using the JVM default charset — so for chunk bytes outside ASCII to survive the round trip, the server JVM should run with `-Dfile.encoding=ISO-8859-1` (as the rest of the wire layer already assumes).

Example — mint a 1-hour ticket for user id `1`:

```java
String ticket = SSOTokenizer.generate(1);                 // default 1h TTL
String ticket = SSOTokenizer.generate(1, 7200);           // 2h TTL
String ticket = SSOTokenizer.generate(1, 3600, 0);        // explicit x
```
